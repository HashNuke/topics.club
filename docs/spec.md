# topics.club product spec

## Goal

Build `topics.club`, a web-based IRC client for a new generation of users. The app should preserve IRC's openness and protocol compatibility while hiding IRC-specific setup complexity behind topic-first discovery and simple OAuth sign-in.

Users should think in terms of joining interesting topics. Internally, each topic is an IRC channel on an IRC server. The app connects the user's IRC session, joins the channel, and opens the chat window without making the entry path feel like IRC setup.

## Product principles

- Topic-first onboarding: users discover topics before they need to understand servers, networks, or channel names.
- Transparent but simple IRC: the UI may show the underlying server and channel when useful, but the primary language should be topics and conversations.
- Escape hatches for IRC users: users can also join other IRC servers and their own channels directly.
- Minimal, dark, responsive interface: use `docs/design.html` as the starting visual direction.
- React-based client: build the chat frontend in React with component tests so the component model can later inform a React Native mobile port.
- TDD workflow: backend behavior and frontend components should be developed with tests first or alongside implementation.

## Primary flow

1. The landing page shows a fun, browsable list of suggested topics.
2. Each topic represents an IRC server and channel.
3. When a visitor clicks a topic and is not signed in, the app asks them to sign in or sign up with OAuth.
4. Google OAuth is available in production-like environments.
5. The developer OAuth provider is also shown in development mode so local testing is easy.
6. After sign-in, the app takes the user to the chat interface.
7. The originally requested topic is autojoined.
8. The joined channel opens as the active chat window.

## Chat interface

The public landing page is mounted at `/`. The main React IRC client is mounted at `/chat`.

Required layout:

- Top bar: active-buffer context and a channel notification bell when a channel is selected.
- Left sidebar: joined chat servers and channels.
- Server rows in the left sidebar include their own notification bell.
- Left sidebar discover entry: opens a topic discovery view using the same topic data and visual language as the landing page.
- Center pane: active chat messages and message composer.
- Right sidebar: users currently present in the active channel.

The design must be mobile responsive. On smaller screens, sidebars can collapse behind navigation controls or drawers, but the active conversation and composer must remain easy to use.

## Topic discovery

The app should fetch or maintain a list of popular IRC channels and present them as topics. The visible topic name is the IRC channel name, but user-facing copy should not describe it as an "IRC channel" on the landing page or discover page.

Discovery is the primary entry path, but it is not the only path. Signed-in users should be able to manually join other IRC servers and channels that are not part of the suggested topic list.

Each topic should include enough metadata for the backend to join it:

- Display topic name, using the channel name.
- IRC server or network.
- IRC channel.
- Optional description.
- Optional activity or popularity signal.

Topic cards and rows should support a compact two-line label:

```text
#channelname
on irc.whatever.com
```

The first line should be visually primary. The server line should use smaller, quieter text.

Clicking a topic from either the landing page or in-app discovery should:

1. Ensure the user is authenticated.
2. Create or reuse the user's server connection.
3. Join the mapped IRC channel.
4. Persist the joined channel for the user.
5. Open the chat window for that channel.

## Authentication

Authentication is OAuth based.

- Google OAuth is the main provider.
- Developer OAuth is available in development and test environments.
- Registration, password login, and magic-link login are available only in development and test;
  production exposes only Google sign-in and logout.
- If an unauthenticated user selects a topic, the requested topic must survive the auth redirect so it can be joined after sign-in.

Authenticated Phoenix routes should use the router-level auth pipeline generated by `phx.gen.auth`, including `:require_authenticated_user` where required. Code should pass `current_scope` to context functions and use `current_scope.user` when filtering user-owned data.

## IRC runtime

Use the Elixir IRC client library being built in `~/projects/ircxd`.

Runtime expectations:

- Keep one IRC session process per `{user_id, server_connection_id}`.
- Supervise sessions under `TopicsClub.Irc.SessionSupervisor`.
- Register sessions in `TopicsClub.Irc.SessionRegistry`.
- Run exactly one IRC engine service. Combined mode uses one BEAM node; split mode may use a gateway and engine node, but the engine remains a deployment-enforced singleton until database-backed ownership leases and fencing exist.
- Reuse an existing session when the same user joins another channel on the same server.
- Use local InspIRCd and irssi installations for development and integration testing.

The UI should account for real IRC data, including:

- Server connection state.
- Joined channels.
- Channel user lists.
- Channel messages.
- Nicknames.
- Mentions.
- Topic metadata where available.
- Join, part, quit, and nickname change events where useful.

## Messages and retention

Messages are persisted per user and channel for short-term continuity.

- User-configurable retention is from 1 to 3 days.
- The maximum retention is 3 days.
- `TopicsClub.Chat.Retention.prune/1` enforces retention after inbound message persistence.
- Message history older than the user's configured retention should be deleted.

## Notifications

The PWA and desktop browser experience supports mention-only notifications.

- Server notification controls live in server rows; channel controls live in the active channel's top bar.
- Each control shows one of four states: enabled, muted, available but not enabled on this device, or unavailable in the current browser context.
- The user requests browser permission explicitly by clicking a notification control.
- Per-server and per-channel preferences are persisted independently; a muted server suppresses its channel notifications.
- The backend queues eligible mentions for Web Push. The service worker displays them only when no visible TopicsClub window is open.
- Realtime socket events update in-app state and notification preferences, but never create browser notifications.

## Backend API

The React client talks to same-origin JSON endpoints under `/api/*` using the existing session cookie and CSRF token from the root layout.

The API should cover:

- Suggested topics.
- Current user's server connections.
- Joined channels.
- Joining a topic.
- Opening or fetching channel history.
- Sending messages.
- Message retention settings.
- Notification-related mention events through the realtime channel flow.

HTTP client code in Phoenix should use the included `Req` library when external HTTP requests are needed.

## Realtime updates

Realtime browser updates flow through:

- `TopicsClubWeb.UserSocket`
- `TopicsClubWeb.UserChannel`

Expected realtime events include:

- New channel message.
- Mention.
- User list changes.
- Channel join success or failure.
- Server connection status changes.

## Frontend requirements

- Use React for the IRC client experience.
- Keep components portable enough that a future React Native app can share concepts and some business logic.
- Write frontend tests for React components and critical user flows.
- Keep the design minimalistic, dark-mode friendly, and responsive.
- Use Floating UI (`https://floating-ui.com/`) for tooltips and popover menus when the React client needs them.
- Do not rely on external script tags from templates; frontend dependencies should be bundled through the supported app assets.

## Testing strategy

Development should be TDD for both backend and frontend.

Backend tests should cover:

- Topic selection and auth redirect continuation.
- Joining topics as server/channel pairs.
- Session reuse for the same user and server.
- Message persistence and retention pruning.
- API authorization and user scoping.
- Realtime events emitted from IRC activity.

Frontend tests should cover:

- Landing topic list rendering.
- OAuth prompt when selecting a topic while signed out.
- Developer OAuth button visibility in development mode.
- Autojoin continuation after sign-in.
- Discover view topic rendering.
- Joining a topic from discover.
- Left sidebar server/channel navigation.
- Right sidebar channel user list rendering.
- Notification bell permission states.
- Web Push notification suppression while an TopicsClub window is visible.

Integration testing can use the local InspIRCd server and irssi as a second IRC client to verify realistic IRC behavior.
